# ADR-0004：工程里程碑只使用自动化出口门禁

- 状态：Accepted
- 日期：2026-08-14
- 决策者：doper maintainers
- 关联设计：`docs/design.md` §2、§15、§16、§18

## Context

P0/M0 原计划把物理设备分配、真实输入法、业务登录态和外部不可变存储作为出口
条件。这些条件不由仓库或 CI 控制，会使已经完成且验证通过的代码长期显示为未完成，
也无法让任意贡献者稳定复现结果。

真机和真实业务数据仍然重要，但它们回答的是“某个平台/部署是否可以进入支持矩阵”，
不是“仓库中的工程工作是否完成”。两者必须分别管理。

## Decision

- P0/M0 及后续工程里程碑只由自动化、可重复、可在 CI 运行的检查决定完成状态。
- P0/M0 的统一自动门禁为 `pnpm m0:check`；当前等价于完整 `pnpm check`，覆盖格式、
  lint、类型、单元/属性测试、契约、生产构建、WASM 预算、Clippy 和 Rust 测试。
- 物理设备性能、真实 IME、业务 COOP/COEP 和外部存储恢复归入“平台资格认证”。
  `pnpm platform:qualify` 保留严格七角色、两组 5+15、原始样本和证据完整性检查。
- 缺少平台资格证据时，该平台状态为 `unqualified`，不得对外声称已在该平台达到
  性能或输入法兼容目标；但它不阻止工程里程碑完成，也不阻止继续实现下一阶段。
- 自动化无法忠实模拟的性能、软键盘和候选窗行为，不使用浏览器模拟数据冒充真机
  结论。未来若接入可编程设备云，它运行相同 `platform:qualify` 契约并作为资格证据，
  不改变工程出口定义。

## Consequences

- 里程碑状态可以由仓库证据客观复现，不再依赖设备采购、账号或人工操作。
- 产品发布和平台支持声明仍可比普通合入采用更严格的资格条件。
- 设计、计划和审计必须明确区分 `engineering complete` 与 `platform qualified`。
- 原 `m0:evidence` 命令保留为 `platform:qualify` 的兼容别名，不再代表 M0 工程出口。

## Verification

- `pnpm m0:check` 在本地与 GitHub CI 执行同一组检查。
- 契约测试继续验证平台报告、IME 录制、证据 manifest 和资格审计器。
- `platform:qualify` 仍失败关闭：没有正式设备证据时不会产生虚假的平台认证。

## Rollback

若将来所有必需环境都由稳定的自动设备云提供，可以把对应任务加入
`pnpm m0:check` 或发布 workflow。回滚必须先证明任务可无人值守、可重复且不会因
外部账号或设备配额使普通工程提交随机失败；不能直接恢复人工前置条件。
